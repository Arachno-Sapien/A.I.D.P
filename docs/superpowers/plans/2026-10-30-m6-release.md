# M6 v0.1 Release Implementation Plan

> **Status: draft, waiting for the human's review and answers to D1 to D6.** Do not start Task 1 before the human approves. After Task 4, stop for a review before starting Task 5.

> **For agentic workers:** execute task by task, in order, inline in one session (Tasks 5 and 6 share config files). In Claude Code, `superpowers:executing-plans` fits; in other tools, follow the steps directly. Steps use checkbox (`- [ ]`) syntax. **Do not tick any milestone box, in any file, until the human confirms the checks in Task 8. Do not push, run the Release workflow or publish a release; the human does.** If another agent works in the same checkout, use a git worktree (known-issues, 2026-10-30).

**Goal:** v0.1 ships as CI-built installers for Windows, macOS and Linux on GitHub Releases, updates itself from one version to the next with signed updates, stays under its RAM targets, and has been used on an 8 GB machine with a real project open.

**Architecture:** CI runs the gate on all three OSes. A manually started Release workflow builds every installer with `tauri-action` and leaves a draft release with a `latest.json` the updater reads. The updater plugin is driven from Rust through three typed commands; the UI never calls plugin commands, so no capability permission is added. macOS and Linux differences the code doesn't handle yet (the PATH a Finder-launched app gets, Ollama's macOS location, the shell named to the model) are fixed in Rust. The M4 and M5 carry-overs land before the release.

**Tech stack:** what M5 has, plus `tauri-plugin-updater` 2 (signed updates; the design names auto-update) and, on Windows only, `windows-sys` 0.61 (already in `Cargo.lock`; the job object). No npm package.

**Spec:** [docs/design.md](../../design.md): "Milestones → M6", "Risks and open questions", "Stack" (Builds). Decision 0016 (three OSes). Rules: [AGENTS.md](../../../AGENTS.md) sections 3, 4, 6 and 7. Carry-overs: `docs/phases/M4.md` and `docs/phases/M5.md`, "What's left → To M6".

## Global Constraints

- **Workflow:** the gate (AGENTS.md section 8) before every commit; one commit per task; update `.ai/memory/progress.md` after each.
- **Rust:** no `unwrap()`/`expect()` outside tests; no `std::sync::Mutex` guard across `.await`; 64-bit integers never cross the IPC (download progress is whole kilobytes as `u32`). `unsafe` only for the Win32 job-object calls and the one `set_var`, each block with a `// SAFETY:` line.
- **The update signing key:**
  - The human generates it and keeps the private key and its password. They go into GitHub secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, plus the human's own backup. Losing the key means existing installs can't be updated again.
  - The private key and its password are never in the repo, chat, logs, memory files or CI output. Agents never run `tauri signer generate`.
  - The **public** key is safe to commit: `plugins.updater.pubkey` in `tauri.conf.json`.
- **Updates install only when the user clicks Install,** and never while a file has unsaved changes. Nothing downloads in the background.
- **The human's steps:** pushing, starting the Release workflow, publishing a draft release, and every check on a real machine.
- **Versions** live in three files that must match: `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`. The release tag is `v` + that version.
- **Verified against sources on 2026-10-30** (do not re-research; if the compiler, CI or a live check disagrees, trust them):
  - Tauri updater (`.claude/skills/tauri/references/features-updater.md`):
    - Signing can't be turned off. `bundle.createUpdaterArtifacts: true` makes the `.sig` files and needs `TAURI_SIGNING_PRIVATE_KEY` at build time.
    - Config: `plugins.updater.pubkey` (key text, not a path), `plugins.updater.endpoints` (TLS enforced), `plugins.updater.windows.installMode` (`"passive"` default).
    - Rust API: `app.updater()?.check().await? -> Option<Update>`, then `update.download_and_install(|chunk, total| .., || ..).await?` and `app.restart()`. On Windows the installer closes the app itself.
    - Static `latest.json` platform keys: `windows-x86_64`, `darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`. `tauri-action` writes it for GitHub Releases.
  - CI (`distribute-pipelines.md`, `start-prerequisites.md`): the release job needs `contents: write`. Ubuntu build packages: `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`.
  - keyring 4.2 (crate source, `v1.rs`): it picks the Windows Credential Manager, the macOS Keychain, or the Secret Service over zbus on Linux. With no Secret Service, `Entry::new` fails with `NoDefaultStore`, which reaches the UI as `AppError::Keychain`. `appErrorText.ts` already adds "On Linux this needs GNOME Keyring or KWallet." There's no plain-text fallback anywhere.
  - The code today:
    - `tools/command.rs`: `sh -c` in a new process group, killed with `kill -KILL -<pgid>` on macOS and Linux; `cmd.exe` and `taskkill /T` on Windows.
    - `tools/pty.rs`: `$SHELL` on macOS and Linux, `powershell.exe` on Windows.
    - `ollama/process.rs`: `open` / `xdg-open` for the download page.
    - Tests switch commands with `cfg!(windows)`.
- **Assumed, not verified (check where the task says):**
  - A macOS app opened from Finder or the Dock gets `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, so `npm`, `cargo` and `ollama` aren't found (Task 2; the Tauri project ships `fix-path-env-rs` for this).
  - The Ollama macOS app keeps its CLI at `/Applications/Ollama.app/Contents/Resources/ollama` and links `/usr/local/bin/ollama` (Task 2).
  - The MSI bundler rejects non-numeric pre-release versions like `0.1.0-rc.1` (one reason D1 picks NSIS).
  - `tauri build --config <file>` merges a JSON file into the config (Task 6).
  - `bundle.macOS.signingIdentity: "-"` ad-hoc signs, which Apple silicon needs to start the app at all (Task 6).
  - `tauri-action` lists both `darwin-*` keys for a `universal-apple-darwin` build (Task 6 checks `latest.json`).
  - The updater installs AppImage updates on Linux; `.deb` installs update by downloading the new `.deb` (Task 5 checks the pinned plugin's docs).
  - The plugin's default TLS may pull `aws-lc-rs`, which breaks Windows builds (decision 0006). Task 5 checks `cargo tree -i aws-lc-rs` is empty.

## Before you start (human)

- **D1, installer formats.** Default:
  - Windows: NSIS `.exe`. It installs per user with no admin prompt and accepts `-rc` versions; MSI is dropped.
  - macOS: one universal `.dmg` for Apple silicon and Intel.
  - Linux: `.AppImage` (any distro; updates itself) and `.deb` (Debian, Ubuntu).
  - Not built: MSI, `.rpm`, Flatpak, Snap, ARM Linux or ARM Windows.
- **D2, code signing.** Default:
  - Windows unsigned, as the design's risk row already says. SmartScreen shows "Windows protected your PC" → More info → Run anyway.
  - macOS ad-hoc signed, not notarized, so there's no paid Apple Developer account ($99 a year). On first open macOS blocks it; the user allows it in System Settings → Privacy & Security → Open Anyway.
  - The user guide shows both. The alternative is buying certificates now (Apple Developer Program; for Windows, a code-signing certificate or Azure Trusted Signing) and adding their secrets to the Release workflow.
- **D3, updates.** Default:
  - The app checks GitHub once, 10 seconds after it starts. A Settings switch "Check for updates at start" turns that off, and a **Check for updates** button checks on demand.
  - A found update shows a bar: "A.I.D.P 0.1.1 is available." with **Install and restart** and **Later**.
  - Install is refused while a file has unsaved changes. A streaming reply or a running command is stopped, the same as quitting.
- **D4, release process.** Default:
  - The human starts the **Release** workflow on `main` from the Actions tab. It builds every installer and leaves a draft release `v{version}`; the human checks the files and publishes it.
  - The update test uses two release candidates, `0.1.0-rc.1` and `0.1.0-rc.2`, published as normal releases (not "pre-release"), so the updater's `releases/latest` address finds them. Then comes `0.1.0`, which rc users also update to.
  - **You'll need first:** generate the update key on your machine in PowerShell with `npx tauri signer generate -w "$env:USERPROFILE\.tauri\aidp.key"` and choose a password. Add the private key's text and the password as repository secrets (GitHub → Settings → Secrets and variables → Actions) named `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Back the key file up. Give the agent only the **public** key (`aidp.key.pub`).
- **D5, testing without a Mac or a Linux machine.** Default:
  - CI runs the whole gate on Windows, macOS and Linux.
  - An Ubuntu 24.04 VM with 8 GB of RAM (VirtualBox on the dev laptop) is both the Linux hand-check and the 8 GB machine.
  - macOS gets no hand-check before 0.1.0; the release notes say so and ask for reports.
  - The alternative is waiting for a volunteer with a Mac, or a real 8 GB Windows machine as well.
- **D6, the carry-overs.** Default: all of these go into M6.
  - A job object, so Stop on Windows also ends processes whose parent already exited.
  - Model commands with a full-width character (U+FF01 to U+FF5E, such as `＂`) are refused like hidden characters; some Windows programs turn them into the ASCII character they look like. A user who needs one types the command in the terminal.
  - The Agent label never gets cut off.
  - A partial reply is saved when the folder changes mid-reply.
  - The alternative for full-width characters is highlighting them on the command card instead of refusing.

## Decided in this plan (record them in docs/phases/M6.md)

- **No plugin commands reach the UI.** The updater runs behind `check_update` and `install_update`, and `capabilities/default.json` stays `core:default` only.
- **Updater artifacts only in CI.** `createUpdaterArtifacts` lives in `src-tauri/tauri.updater.conf.json`, which the Release workflow passes with `--config`. A local `npm run tauri build` keeps working without the private key.
- **macOS and Linux get the login shell's PATH.** At start, before any thread, the app asks `$SHELL -ilc` for `PATH` (5-second limit, markers around the value) and uses it when the call succeeds. Commands, the terminal and the Ollama lookup then find what the user's own terminal finds. It runs the user's own shell startup files, the same as opening their terminal.
- **The model is told which shell runs its commands:** `cmd.exe` on Windows, `sh` on macOS and Linux.
- **The macOS terminal starts a login shell** (`-l`), as Terminal.app does.
- **No new Linux keychain code.** The existing error already names GNOME Keyring and KWallet; Task 8 confirms it on the VM.
- **Update errors get their own kind,** `AppError::Update { message }`, shown as its message.

## Not in M6 (do not build)

Paid code signing or notarization (unless D2 changes), MSI, `.rpm`, Flatpak, Snap, Homebrew, winget, ARM builds, update channels, background or silent installs, delta updates, crash reporting or telemetry, chat export (open question), command auto-approve (open question).

## Review Focus

1. **Install at a bad moment:** unsaved files (refused with a message), a streaming reply or running command (stopped like quit). Tests: Task 5.
2. **The update check failing:** offline, GitHub down, a `latest.json` without this platform, a bad signature. At start it stays quiet; the button shows a message; nothing crashes or installs. Tests: Task 5.
3. **Versions out of step** across the three files, which would tag the release wrongly. Test: Task 5.
4. **The login-shell PATH:** a startup file that hangs (limit), prints noise (markers), or a missing `$SHELL` (keep the PATH as is). Tests: Task 2.
5. **Stop ending everything it started,** on Windows too, including a process detached from the shell. Tests: Task 3.

### Task 2: macOS and Linux differences

**Produces:**
- `login_path.rs`:
  - `pub fn extract_path(output: &str) -> Option<&str>`: the text between the first `__AIDP_PATH_START__` and the next `__AIDP_PATH_END__`, if it isn't empty.
  - `pub fn run_with_limit(cmd: std::process::Command, limit: Duration) -> Option<String>`: stdin and stderr null, stdout captured; the process is killed and `None` returned once `limit` passes.
