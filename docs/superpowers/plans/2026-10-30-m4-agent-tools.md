# M4 Agent Tools and Terminal Implementation Plan

> **Status: waiting for the human's review and answers to D1 to D3.** Execute from Task 1 only after approval. After Task 7, stop for a review before starting Task 8.

> **For agentic workers:** execute task by task, in order, inline in one session (the tasks share files). In Claude Code, `superpowers:executing-plans` fits; in other tools, follow the steps directly. Steps use checkbox (`- [ ]`) syntax. **Do not tick any milestone box, in any file, until the human confirms the live check in Task 12. Do not push; the human decides.**

**Goal:** In the workspace's AI panel, a model with tool calling can list, read and search the open folder on its own, propose edits and new files that reach the disk only after Accept, and ask to run commands that run only after Run. A terminal panel at the bottom runs the user's own shell in the folder.

**Architecture:** The tool loop runs in Rust (`src-tauri/src/tools/`). One `run_agent` command streams a reply through the same `Channel<ChatEvent>` as M3. When the model asks for tools, Rust runs each call itself, with path checks and the secret filter from `workspace/`. Read-only calls run at once. Edits, new files and commands are first sent to the UI as a `ToolCall` event, and Rust waits on a one-shot answer from `answer_tool`. Then the loop sends the results back to the model and continues until the model replies without tools. Both adapters get tool calling behind the same `ModelProvider` trait. Each adapter returns its own assistant message, which the loop sends back unchanged on the next call. That keeps Claude's thinking blocks valid. The terminal is a `portable-pty` session streaming text to xterm.js through a second `Channel`.

**Tech stack:** what M3 has, plus Rust `tokio` 1 as a direct dependency (already in the tree through Tauri) and `portable-pty` 0.9; JS `@xterm/xterm` 6 and `@xterm/addon-fit` 0.11.

**Spec:** [docs/design.md](../../design.md): "Model layer", "Coding workspace" (M4), "Workspace and tool security", "Data model", "Screens and user flows" (Workspace, "Flow: work on code with AI" step 5), "Milestones -> M4", "Risks" (harmful command, prompt injection, small models and tools). Rules: [AGENTS.md](../../../AGENTS.md) sections 4, 6 (both lists) and 7. Carry-overs: `docs/phases/M3.md`, "What's left -> To M4".

## Global Constraints

- **Workflow:** the gate (AGENTS.md section 8) before every commit; one commit per task; update `.ai/memory/progress.md` after each; every new dependency gets a one-line reason in its commit body.
- **Rust:**
  - No `unwrap()` or `expect()` outside tests.
  - Never hold a `std::sync::Mutex` guard across an `.await`. In `Approvals`, take the sender out of the map, drop the guard, then send.
  - File and folder work in `tools/` runs inside `tokio::task::spawn_blocking`, so it runs on whichever runtime drives the loop (Tauri's in the app, the test's in tests).
  - 64-bit integers cannot cross the IPC: step ids are `u32`, terminal sizes `u16`, exit codes `i32`.
- **Tool security (AGENTS.md section 6, workspace list, as it applies to M4):**
  - **One folder.** Every path a model sends goes through `workspace::paths::resolve`, or the new `resolve_new` for files that do not exist yet. The same refusals apply as for the UI: `..`, absolute paths, drive prefixes, `:`, and links pointing outside.
  - **Edits are proposals.** `apply_edit` and `apply_create` are called only after `Answer::Yes` from `answer_tool`.
  - **Every model command is approved.** `run_command` is called only after `Answer::Yes`. No code path, setting or test helper answers on the user's behalf. There is no "approve all".
  - **Tool output is data.** The agent system prompt says so. Nothing in a tool result can change what needs approval, because approval is decided by the tool's name in Rust, never by the model or the result.
  - **Secrets stay out of prompts.** `list_files`, `read_file` and `search` skip secret-looking files. `edit_file` refuses them too, because a match or no-match would reveal their contents.
  - **Warn without git.** The first tool edit Accept in a folder without git asks first, the same `needsGitConfirm` as M3.
- **Loop invariants (tested):** the approval is registered **before** its `ToolCall` event is sent, so an instant answer is never lost. Every `ToolCall` event is followed by exactly one `ToolResult` event with the same id, including when the reply is stopped (`stopped`). Tool calls in one model reply run one at a time, in the order given.
- **`src/lib/bindings.ts`** is regenerated by `cargo test`, committed, never edited by hand. **Component tests** register `afterEach(cleanup)`. CodeMirror stays only in `cm.ts`, and xterm.js only in the new `term.ts`. Component tests mock both.
- **Verified against sources on 2026-10-30** (do not re-research; if the compiler disagrees, trust the compiler):
  - **OpenAI-compatible tool calling** (OpenAI Chat Completions format, also used by OpenRouter, Groq, DeepSeek and Gemini's compat endpoint):
    - Request: `"tools": [{"type":"function","function":{"name","description","parameters": <JSON Schema>}}]`.
    - Stream: `choices[0].delta.tool_calls[]` items carry `index`. The first chunk for an index has `id`, `type` and `function.name`; later chunks append `function.arguments` text. `finish_reason` is `"tool_calls"`, though some providers send `"stop"`, and `"length"` means the reply was cut off.
    - Replay: `{"role":"assistant","content": <text or null>,"tool_calls":[{"id","type":"function","function":{"name","arguments": <the raw string>}}]}`, then one `{"role":"tool","tool_call_id","content"}` per call.
    - OpenRouter's `GET /models` lists `supported_parameters` per model; `"tools"` in it means tool calling works.
  - **Anthropic tool calling** (the claude-api skill: `curl/examples.md`, `shared/tool-use-concepts.md`, `shared/model-migration.md`):
    - Request: `"tools": [{"name","description","input_schema"}]`.
    - Stream:
      - `content_block_start` with `content_block` `{"type":"tool_use","id","name","input":{}}`;
      - `content_block_delta` with `delta` `{"type":"input_json_delta","partial_json"}`;
      - `content_block_stop`;
      - `message_delta` `stop_reason` `"tool_use"`.
    - Thinking blocks stream as `content_block_start` `{"type":"thinking","thinking":"","signature":""}` plus `thinking_delta` (`thinking`) and `signature_delta` (`signature`) deltas. `redacted_thinking` blocks arrive whole in `content_block_start`.
    - Replay: the assistant `content` array unchanged, then one `user` message holding every `{"type":"tool_result","tool_use_id","content", "is_error": true only on errors}`.
    - **Current Claude models always think.** Removing or editing a thinking block inside a tool loop gives a 400 on accounts created on or after 2026-08-31. Dropping *all* thinking blocks of earlier turns is allowed, because removing a leading run of blocks is.
    - All Claude models support tools.
  - **`eager_input_streaming` stays off.** The skill advises leaving it off behind custom base URLs and proxies, and the buffered default validates the tool input for us.
  - **Versions:**
    - npm: `@xterm/xterm` 6.0.0 and `@xterm/addon-fit` 0.11.0. Install with `^`.
    - crates.io: `portable-pty` 0.9.0.
    - `tokio` 1.54.1 is already in `Cargo.lock` through Tauri.

## Before you start (human)

- **D1, widen the secret-file list (changes security rule 6, which AGENTS.md and the design doc keep word for word).** A push security review on 2026-10-30 called today's list incomplete. It matters most now, because the model reads files on its own. Proposed new rule 6:
  > **Secrets stay out of prompts.** Files that look like secrets (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.tfvars`, `id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `id_dsa*`, `.npmrc`, `.pypirc`, `.netrc`, `_netrc`, `.git-credentials`) are skipped by `list_files`, `read_file`, and `search`; files containing a private key block (`-----BEGIN ... PRIVATE KEY-----`) are skipped by `read_file` and `search`. Neither is ever sent as context unless the user adds it by hand.

  Default: **yes** (decision 0010). Say "keep the list" to leave rule 6 as it is; Task 4 then skips its D1 steps.
- **D2, limits.** A command stops after 120 seconds. The model gets the last 20,000 characters of command output. `read_file` returns at most 100,000 characters per call (the model asks for line ranges beyond that). `list_files` returns 500 entries and `search` 100 matches. One message allows at most 25 model calls before the loop stops and says so. Default: these values, as constants in `tools/mod.rs`, with no setting yet.
- **D3, shells.** Model commands run with `cmd.exe /D /S /C "<command>"` on Windows (fast start, the exact string runs as shown) and `sh -c` elsewhere; the tool description tells the model which. The terminal panel runs Windows PowerShell (`powershell.exe -NoLogo`, on every Windows 10/11) and `$SHELL` (else `/bin/sh`) elsewhere. The alternative is PowerShell for model commands too: slower to start, and models write cmd-style commands less often wrong. Default: as described (decision 0011).
- **Tool-capable model for Task 12:** OpenRouter's model page lists "tools" under supported parameters. If your free model doesn't have it, choose a free one that does. Some reasoning models need extra data sent back with tool calls (see Review Focus 5). If one fails that way, try another.

## Decided in this plan (record them in docs/phases/M4.md)

- **The loop lives in Rust** (design: `tools/` holds "the tool-call loop, approvals"). The UI only renders events and answers approvals.
- **Agent mode is a switch in the AI panel**, **Agent**. It is on by default when the model's capability says it supports tools, off when unknown, and disabled with "This model can't use tools" when it says no. Turning it on for an unknown model is the "user-set" capability from the design: if the provider refuses tools, the error says to turn Agent off. Off means exactly the M3 workspace (`send_message`, chips, Apply).
- **Capability source:**
  - A new nullable `models.supports_tools` column (migration 3).
  - OpenRouter: from `supported_parameters`.
  - Anthropic: always yes.
  - Other OpenAI-compatible providers: unknown.
  - Rows saved before M4 stay unknown until the user saves Choose models again.
  - `supports_vision` is not added: nothing uses it in v1 (no scaffolding). The design's "Data model" is updated to say so.
- **Between user messages the model sees only text.** The UI sends the conversation as text, as in M3. Tool calls, file contents and thinking from earlier messages are not sent again. Within one message, every model call gets the full tool history verbatim. This keeps requests small and stays inside the thinking-block rule above. The model re-reads files when it needs them.
- **`read_file` returns plain text without line numbers**, so `edit_file`'s `old_text` can be copied exactly. A header line gives the path and the line range.
- **`edit_file` replaces text that must occur exactly once**. Line endings are normalised to `\n` on both sides; the file keeps its own line ending and BOM when written (M3's `write_file`, with the version read at proposal time, so a change on disk in between gives `ChangedOnDisk` and the model is told to read again).
- **The diff is against the file on disk.** If the file is open with unsaved edits, Accept still writes the disk; the dirty tab is not reloaded, and its next save meets M3's "changed on disk" prompt, so nothing is lost silently. A clean open tab reloads after Accept.
- **`create_file`** only creates a path that does not exist, creates missing folders inside the project, and writes LF without BOM. Secret-looking names may be created (the user sees the content in the diff; reading is what the rule protects).
- **`search` is a literal, case-insensitive substring search** (no regex: no new dependency), over text files up to 2 MB, skipping `.gitignore`d and secret files, at most 20,000 files walked.
- **Commands:** working folder is the project root; no stdin (a prompt for input gets end-of-file, so nothing hangs); stdout then stderr, the tail kept; on timeout or Stop the whole process tree is killed (`taskkill /T /F` on Windows, the process group elsewhere). `// ponytail:` output is shown when the command ends, not live; stream it if users ask.
- **One proposal at a time.** M3's Apply is refused while a tool proposal waits ("Answer the proposed change first.").
- **Switching or closing the folder stops a running agent reply** (`stopReply("workspace")`), so the loop never writes into a folder the user has left.
- **Anthropic:** tool requests use `max_tokens` 32,000 (thinking and a whole new file share the budget; 8,192 cuts them off); plain chat keeps 8,192. A reply cut off at `max_tokens` or `length` while a tool call is open is an error, and its tools never run.
- **A provider that refuses tools** (HTTP 400 or 404 whose body mentions both "tool" and "support") maps to `ProviderError::Provider { message: TOOLS_UNSUPPORTED }`. No new error kind, so the normalized list in AGENTS.md stays as it is.
- **The terminal:** one per app; starts when the panel opens; killed when the panel closes or the folder changes; xterm.js loads lazily on first open, so idle RAM is untouched. Commands typed there are the user's own and need no approval (design).

## Review Focus

1. **Paths a model invents:** `/src/a.ts`, `C:\x`, `src\..\..\x`, `~/x`, `new/../../x` for `create_file`, and a junction to outside followed by a new file name. All refused with the "relative to the project folder" text. Tests: Task 4 (`resolve_new` table), Task 5.
2. **Secrets through a side door:** a `search` that matches inside `.env`, `list_files` showing `id_rsa`, a link named `notes.txt` pointing at `.env`, `edit_file` used as a guessing oracle on `.env`, and (D1) a `config.txt` holding a private key. Tests: Tasks 4, 5, 7.
3. **Runaway commands:** a grandchild process surviving Stop or the timeout; output of megabytes; a command waiting for input. Tests: Task 6.
4. **A loop that never ends:** Stop while an approval waits; a folder switch while an approval waits; a model that calls tools forever. Tests: Tasks 7, 8.
5. **Provider quirks:**
   - parallel calls with interleaved indexes;
   - missing tool-call ids;
   - `finish_reason` `"stop"` with tool calls;
   - arguments that are not JSON;
   - Gemini's compat endpoint putting a thought signature in an extra field of the tool call, which must be sent back (keep unknown keys of each streamed tool-call object).
   
   Known gap: OpenRouter's `reasoning_details` are not sent back. If a reasoning model rejects the second call for that, record it in known-issues and choose another model. Tests: Tasks 2, 3.

**OpenAI-compatible adapter:**
- Request: `"tools"` is added only when `req.tools` is non-empty (Groq rejects an empty array). The `messages` array is the chat messages, then for each round: `round.assistant` as is, then one `{"role":"tool","tool_call_id","content"}` per result. Content is prefixed with `"Error: "` when `is_error`, because OpenAI has no error flag.
- Stream: accumulate tool calls in a `BTreeMap<u32, PartialCall { id, name, arguments: String, extra: serde_json::Map }>`.
  - The key is `index`, or the item's position in the array when `index` is missing.
  - `id` and `name` are set when present and non-empty; `arguments` are appended.
  - Any other keys of the item (except `index`, `type`, `function`) are copied into `extra`. Gemini's thought signature travels there.
  - At the end, a missing id becomes `call_{index}`.
- End: `finish_reason` `"length"` with any tool call gives `Provider { message: "The reply was cut off before its tool call was complete." }`. Otherwise, any accumulated calls are returned whatever the finish reason.
- `assistant` = `{"role":"assistant","content": <text, or null when empty>, "tool_calls": [{"id","type":"function","function":{"name","arguments"}, ...extra}]}`. `tool_calls` is left out when there are none.

### Task 3: Anthropic tool calling

**Produces (`anthropic.rs`):**
- Request: `"tools": [{"name","description","input_schema"}]` only when non-empty; `max_tokens` 32,000 when tools are present, else 8,192 (constants `MAX_TOKENS`, `MAX_TOKENS_WITH_TOOLS`). After the chat messages, for each round: `round.assistant` as is, then `{"role":"user","content":[{"type":"tool_result","tool_use_id","content", "is_error": true}]}` with `is_error` written only when true.
- Stream: blocks are kept by `index` in a `BTreeMap<u32, serde_json::Value>`, starting as the `content_block` of `content_block_start`. Deltas by type:
  - `text_delta`: appends to `text` and sends `ChatEvent::Delta`.
  - `thinking_delta`: appends to `thinking`.
  - `signature_delta`: appends to `signature`.
  - `input_json_delta`: appends `partial_json` to a buffer for that index.
  - Other types are ignored.
  
  At `content_block_stop` of a `tool_use` block, the buffer is parsed (empty means `{}`) into the block's `input`. Invalid JSON keeps `input` `{}` in the block, and the `ToolCall` gets `Value::String(raw)`. `StreamEvent` gains `ContentBlockStart { index: u32, content_block: Value }`, `ContentBlockDelta { index: u32, delta: Value }` and `ContentBlockStop { index: u32 }`. The M2 refusal and error handling stay.
- `stop_reason` `"max_tokens"` with any `tool_use` block gives the "cut off" error from Task 2.
- `assistant` = `{"role":"assistant","content":[blocks in index order]}`. Thinking and redacted thinking blocks are kept unchanged. `tool_calls` = the `tool_use` blocks.

### Task 6: The command runner

**Produces (`tools/command.rs`):**
- `pub struct CommandResult { pub exit_code: Option<i32>, pub output: String, pub timed_out: bool }`
- `pub enum CommandEnd { Finished(CommandResult), Stopped }`
- `pub async fn run_command(root: &Path, command: &str, timeout: Duration, cancel: &CancellationToken) -> Result<CommandEnd, WorkspaceError>`
- `pub fn tail(text: &str, max_chars: usize) -> String`. When cut, it returns `[earlier output cut]\n` plus the last `max_chars` characters, cut on a char boundary.

How:
- Build a `std::process::Command`, then convert it with `tokio::process::Command::from`, with `kill_on_drop(true)`.
  - Windows: `cmd.exe` with args `/D`, `/S`, `/C`, then `raw_arg(format!("\"{command}\""))`, and `creation_flags(0x0800_0000)` (no console window).
  - Elsewhere: `sh -c command` and `process_group(0)`.
- `current_dir(root)`, `stdin(null)`, stdout and stderr piped.
- Two reader tasks each keep the last 64 KiB of their stream.
- `tokio::select!` over the child's exit, `tokio::time::sleep(timeout)` and `cancel.cancelled()`.
  - On timeout or cancel: kill the tree, then wait for the child. Windows: `taskkill /T /F /PID {pid}` with the same no-window flag. Elsewhere: `kill -KILL -- -{pid}`.
- `output` = stdout, plus `\n--- stderr ---\n` and stderr when stderr is not empty, then `tail(.., OUTPUT_LIMIT)`. Decoded with `String::from_utf8_lossy`.

The loop:
1. Put `{role: system, content: agent_system()}` first, ahead of any system messages the UI sent.
2. Up to `MAX_STEPS` model calls. Each call is `stream_chat` with `specs()` and the rounds so far, and usage is summed.
   - A reply without tool calls ends the loop with `Ok`.
3. Otherwise, run the reply's calls in order. For each call:
   - Take `id = approvals.next_id()`, then `parse`.
   - A parse error sends `ToolCall { action: Invalid{name}, needs_answer: false }`, then `ToolResult Error`.
   - **list, read, search:** send `ToolCall` (needs_answer false), run the tool in `spawn_blocking`, then send `ToolResult`.
   - **edit:** run `prepare_edit` in `spawn_blocking`.
     - On error: send `ToolCall EditFile{path, before: "", after: ""}` with needs_answer false, then the error.
     - On success: `register` the approval, send `ToolCall EditFile{path, before, after}` with needs_answer true, then `wait`.
     - On Yes: `apply_edit`.
   - **create:** the same flow with `prepare_create` and `apply_create`.
   - **command:** `register`, send `ToolCall RunCommand{command, folder: display_path(&root)}` with needs_answer true, then `wait`.
     - On Yes: `run_command(&root, &command, command_timeout, &cancel)`.
     - The model gets `Exit code {code}\n{output}`, or `Timed out after 120 seconds and was stopped.\n{output}`. The outcome is `Command{..}`.
   - **No:** `declined(..)`.
   - **Stopped** (from `wait` or `CommandEnd::Stopped`): send `ToolResult Stopped`, then return `Err(Cancelled)`.
4. Push `ToolRound { assistant: reply.assistant, results }` and loop. Each result is `ToolOutput { call_id: call.id, content: run.for_model, is_error: run.is_error }`.
5. After `MAX_STEPS` calls: `Err(Provider { message: "The model used 25 tool steps without finishing. Send a message to let it continue." })`.
6. A failed channel send returns `Err(Cancelled)`, the same as the adapters.

- The test reads what the loop sent with `server.received_requests()`.
- Events are captured with `common::capture`. An approval is answered from the test as soon as its `ToolCall` event appears: poll the captured events, then call `approvals.answer`.

### Task 9: Terminal backend

**Produces (`tools/pty.rs`):**
- `#[serde(tag = "event", content = "data", rename_all = "camelCase")] pub enum TerminalEvent { Output(String), Exit }`
- `pub fn take_utf8(buf: &mut Vec<u8>) -> String` returns the longest valid UTF-8 prefix. An incomplete sequence at the end stays in `buf`. Invalid bytes in the middle become U+FFFD and are consumed, so the stream never stalls.
- `pub fn default_shell() -> CommandBuilder` (D3). Windows: `powershell.exe -NoLogo`. Elsewhere: `$SHELL`, falling back to `/bin/sh`, with `TERM=xterm-256color`.
- `pub struct Terminal` holds the master, the writer and the child.
  - `start(root: &Path, shell: CommandBuilder, cols: u16, rows: u16, out: Channel<TerminalEvent>) -> Result<Terminal, WorkspaceError>` sets the cwd to `root`. A `std::thread` reads into a buffer and sends `Output(take_utf8(..))`. On end of file or error it sends `Exit`. If a send fails, it stops.
  - `write(&mut self, data: &str)` and `resize(&self, cols, rows)`. `Drop` kills the child.
  - PTY errors map to `WorkspaceError::Io { message }`.
- `#[derive(Default)] pub struct TerminalState { term: Mutex<Option<Terminal>> }`
- `commands/terminal.rs`, all `async` and all returning `Result<(), WorkspaceError>` (none awaits while holding the lock):
  - `terminal_open(cols: u16, rows: u16, on_event: Channel<TerminalEvent>)` needs the folder (`NoFolder`) and replaces any running terminal.
  - `terminal_write(data: String)`, `terminal_resize(cols: u16, rows: u16)` and `terminal_close()` do nothing when no terminal runs.
- `lib.rs` manages `TerminalState` and registers the four commands.
