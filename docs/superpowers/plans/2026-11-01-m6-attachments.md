# Attachments (images, text files, PDFs) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the user attach images, text or code files, and PDFs to a message in Chat and in the workspace side chat, for 0.1.0-rc.3.

**Architecture:** Rust reads, checks and stores every attachment in the app's data folder under a content hash, and the UI only ever holds attachment IDs and thumbnails. When a message is sent, Rust turns the IDs into what each provider expects: text and PDF text join the message text, and images become each adapter's image block.

**Tech Stack:** Rust (`pdf-extract` 0.12, new, decision 0019; `base64` and `sha2`, already in the tree), tauri-plugin-dialog from Rust, Tauri window drag-drop events in Rust, React + Zustand, tauri-specta.

**Spec:** the human's request of 2026-11-01 ("the Chat mode doesn't allow images & files to be attached") and their choices (images, text files and PDFs; ship as rc.3), `docs/design.md`, AGENTS.md sections 4, 6 and 7.

## Decisions (defaults; the human approves or changes them)

| | Question | Default |
| --- | --- | --- |
| A1 | Kinds and limits | Images: PNG, JPEG, WebP, GIF (checked by their first bytes), up to 5 MB each (Anthropic's limit). Text and code files: valid UTF-8 with no NUL byte, up to 512 KB. PDFs: up to 20 MB, text extracted, up to 200 pages. At most 5 attachments per message. Anything else is refused with a message naming the file |
| A2 | Ways to attach | A paperclip button (Rust opens the file dialog), dropping files on the window (Rust receives the drop; the UI never sends a path), and pasting an image (the UI sends the pasted bytes). Both Chat and the workspace side chat |
| A3 | Storage | Copied into `<app data>/attachments/<sha256>.<ext>`; a PDF's text is saved beside it as `<sha256>.txt`. Message parts store `{ kind: "attachment", id, name, mime, size }`, never the bytes. Deleting a chat removes the files no remaining message refers to |
| A4 | Sending | The UI sends IDs. Rust adds text files and PDF text to the message text as a fenced block headed `File: <name>`; images go as base64 to the adapter: OpenAI-compatible `image_url` data URL, Anthropic `image` block, Ollama `images`. PDFs go as text to every provider, so local models read them too. A PDF with no text layer (a scan) is refused: "This PDF has no text to read" |
| A5 | Models that can't see | Migration 6 adds `models.supports_vision`; Ollama fills it from `/api/show` `capabilities` ("vision"); cloud models stay unknown. With an image attached, a model known not to see blocks Send with "This model can't read images"; an unknown one sends, and any refusal shows as the usual provider error |
| A6 | Showing images | Thumbnails in the composer and in sent messages, from a `read_attachment(id)` command, shown through `blob:` URLs. CSP gains `img-src 'self' blob:` |
| A7 | Secret-looking files picked by hand | Allowed (rule 6 allows what the user adds by hand), with a warning on the chip: "Looks like a secret file" |
| A8 | Context budget | Attached text counts against the model's context window the same way file chips do now (`context.ts` budget); text over the budget is cut, with a note in the chip |

## Global Constraints

- The UI never reads a file or sends a path. Rust opens the file dialog, receives dropped files, and checks every attachment by its first bytes, not its name.
- No new Tauri plugin or capability permission. The dialog is called from Rust (decision 0008), and drag-drop arrives in Rust's window event.
- Keys and request headers are never logged; attachment contents are never logged either.
- `src/lib/bindings.ts` is regenerated by `cargo test`, never edited by hand.
- No `unwrap()` or `expect()` outside tests. Schema changes go through migration 6.
- Adapter tests use wiremock and assert the request body's image shape for each provider.
- The gate (clippy `-D warnings`, cargo test, typecheck, vitest) passes before every commit; docs change in the same commit.
- The version becomes `0.1.0-rc.3` only when both this plan and the themes plan are done.

## Review Focus

1. A file renamed to `.png` that is not an image: refused by its first bytes, never sent (Task 1).
2. A chat with an image is reopened after a restart: the thumbnail shows, and sending again includes the image (Tasks 1 and 3).
3. Deleting a chat whose image another chat also uses: the file stays until the last reference goes (Task 1).
4. An image sent to a local model without vision: Send blocked with the message, nothing reaches Ollama (Tasks 2 and 3).
5. A 20 MB PDF of scanned pages: refused quickly with the no-text message, the app stays responsive (Task 1, extraction on a blocking thread with a 20 s limit).

### Task 1: The attachment store in Rust

**Files:**
- Create: `src-tauri/src/attachments/mod.rs` (kinds, limits, store, clean-up), `src-tauri/src/attachments/pdf.rs` (text extraction)
- Create: `src-tauri/src/commands/attachments.rs`; register in `collect_commands!` in `src-tauri/src/lib.rs`; the drop handler in `lib.rs` setup (`on_window_event`, `WindowEvent::DragDrop`)
- Modify: `src-tauri/Cargo.toml` (`pdf-extract = "0.12"`, `base64 = "0.22"`, `sha2 = "0.10"`), `src-tauri/src/history.rs` (`delete_conversation` calls the clean-up)
- Create: `docs/decisions/0019-attachments.md` (attachments join v0.1 at the human's request; PDF text via `pdf-extract` against provider PDF support and pdfium)
- Test: unit tests in `attachments/mod.rs` and `pdf.rs`; `src-tauri/tests/attachments.rs`

**Interfaces:**
- Produces:
  - `#[derive(Serialize, Deserialize, Type)] pub struct Attachment { id: String, name: String, mime: String, size: u32, kind: AttachmentKind, warning: Option<String> }`
  - `enum AttachmentKind { Image, Text, Pdf }`
  - `AttachmentStore::new(dir: PathBuf)`, with `add(name: &str, bytes: &[u8]) -> Result<Attachment, AppError>`, `read(id: &str) -> Result<Vec<u8>, AppError>`, `text(id: &str) -> Result<Option<String>, AppError>` (the text of a text file or PDF), and `remove_unreferenced(referenced: &HashSet<String>) -> Result<u32, AppError>`.
  - IDs are 64 lowercase hex characters, checked before any path is built.
  - Commands:
    - `pick_attachments() -> Result<Vec<Attachment>, AppError>` opens the dialog;
    - `attach_bytes(name: String, bytes: Vec<u8>) -> Result<Attachment, AppError>` handles paste;
    - `read_attachment(id: String) -> Result<Vec<u8>, AppError>`.
  - The drop handler emits `attachments-dropped` with `Vec<Attachment>`, or with the error text for each refused file.

- [ ] **Step 1: Failing tests:**

  - `limits_are_enforced`: 5 MB + 1 image, 512 KB + 1 text, 20 MB + 1 PDF are refused with the file named in the message.
  - `same_bytes_same_id`.
  - `an_id_that_is_not_hex_is_refused`: `../x`, too short, uppercase.
  - `pdf_text_is_extracted`, using a minimal PDF built in the test with `lopdf`.
  - `a_pdf_without_text_is_refused`.
  - `clean_up_keeps_referenced_files`.
  - `secret_looking_names_get_a_warning`: `.env`, `id_rsa` and `x.pem` get `warning` set.
